INSIGHTS / NETWORK OBSERVABILITY

Process-aware network telemetry: what a domain observation can—and cannot—prove.

Correlating traffic to a Windows process is a different problem from simply capturing DNS packets. A reliable tool needs multiple evidence sources and clear limits on attribution.

22 OCT 2026 · Engineering note based on the public ProcDomainSniffer architecture

1. The engineering problem

A packet capture can describe a connection: addresses, ports, protocols and timestamps. It does not inherently tell an investigator which user-mode process initiated that traffic. Conversely, enumerating processes identifies applications and process IDs, but does not produce a history of observed DNS names.

For application-focused troubleshooting, the useful question is often not “Which hosts did this machine contact?” but “What network evidence is associated with this selected application, and how strong is that association?” The difference matters when several processes share DNS caches, proxies, browser helpers or common endpoints.

2. Capture and process information have different roles

The published ProcDomainSniffer architecture combines a native .NET 8 / WPF interface with Windows ETW / TraceEvent, TShark and Npcap. The UI selects a process; the capture pipeline collects network observations; the correlation layer brings evidence together for domain and endpoint views.

  • Process identity: PID, executable path and selected process context provide a starting point for narrowing observations.
  • Windows event telemetry: ETW can help tie network activity to process-level context, depending on the specific provider and events available.
  • Packet observations: TShark/Npcap can expose packets on capture interfaces, protocol fields and DNS traffic visible at the capture point.
  • Correlation: Events should be related by timing, transport endpoints and observed process context rather than a single coincidental IP address.

This is an architectural separation of responsibilities, not a claim that every network flow can be attributed perfectly.

Important boundary: A DNS lookup associated with a process is evidence of a name-resolution observation, not proof that the same process later connected to that destination or transmitted application data.

3. Why DNS attribution is ambiguous

DNS information is useful, but it is not a complete connection ledger. Consider a few ordinary cases:

  • Resolver caches: A subsequent connection may use a cached IP address without generating a fresh DNS event during the capture window.
  • Shared infrastructure: Multiple domain names can resolve to the same CDN IP address, and the mapping can change over time.
  • Multiprocess applications: A browser or desktop application can delegate network activity to subprocesses or helper services.
  • Encrypted name resolution: DoH or other encrypted resolution can limit the DNS questions visible to a conventional packet capture.
  • Connection reuse: An existing TCP or QUIC connection can carry additional requests without a one-to-one new DNS lookup or new connection event.

That is why “observed domain,” “resolved IP” and “network endpoint” are separate views in the tool. They represent related but non-identical claims.

4. Practical design choices

The public project exposes a focused workspace: process selection, capture settings, live domain events, aggregated domain summaries, domain-to-public-IP observations, network logs and activity/status information. Keeping these views separate makes it easier to inspect what the tool actually observed before forming an attribution.

Useful controls include selecting the capture interface, filtering loopback or internal traffic, searching observations, and exporting evidence for external analysis. Those controls improve analyst workflow but should not silently discard context needed to interpret a result.

For production-grade investigation tools, a stronger record can include a capture timestamp, process identity at observation time, source of evidence, interface, endpoint tuple and an explicit confidence indicator. These are design recommendations, not assertions that every such field currently exists in ProcDomainSniffer.

5. How I would validate the correlation

  1. Open two applications that access different, known test endpoints and start capture before initiating traffic.
  2. Verify process attribution from a direct event source and compare against packet timestamps.
  3. Repeat a request after DNS cache warm-up; note where no new DNS observation appears.
  4. Test concurrent connections from multiple processes to the same destination.
  5. Separate locally observed DNS names from inferred associations; ensure the UI doesn't present inference as direct observation.
  6. Verify filtering and export preserve enough timestamps and network context for an independent review.

These cases expose false positives and evidence gaps earlier than a happy-path demo with one application and one domain.

6. The takeaway

Good security telemetry is not a long list of captured fields. It is a disciplined explanation of what was observed, what was inferred, and what remains unknown. ProcDomainSniffer provides a practical environment to work on that distinction at the process/network boundary.
